# Feasibility: an out-of-tree vLLM plugin for EXL3

Status: research/feasibility only, no code written. `exllamav3` is cloned at the
root of this directory (`0b9745c5`, v1.3.0, 2026-07-31) as a reference checkout;
everything below is grounded in that source plus vLLM's plugin docs/source and
the QTIP/QuIP/YAQA papers and repos.

## Verdict

**Feasible, and the timing is good.** vLLM's own policy is now to push
quantization backends out-of-tree — GGUF and bitsandbytes are being evicted
from core via [RFC #39583](https://github.com/vllm-project/vllm/issues/39583)
for exactly this reason. EXL3 is structurally *easier* to integrate than GGUF
was: it's plain safetensors + HF `config.json`, not a container format, so a
plugin needs none of the loader/config monkey-patches GGUF requires. The
biggest structural win: **exllamav3 already ships working, MIT-licensed,
Python-callable CUDA kernels** (`exllamav3_ext`, via pybind). A vLLM plugin
does not need to write or vendor GEMM kernels — it needs a `QuantizationConfig`
+ `LinearMethod` that calls into exllamav3's existing compiled extension. That
turns this from "build a quantization kernel library" into "build an adapter
layer," which is a much smaller project.

The real risk is not "can this be built" but **tensor parallelism and fused
QKV/gate-up projections**, both of which interact badly with EXL3's blocked
Hadamard transform and per-tensor scale vectors. See "Hard problems" below —
that's where a spike should focus first.

One hard constraint shapes the whole approach: **QTIP, QuIP#, and YAQA are all
GPL-3.0**; vLLM is Apache-2.0. None of that code can be copied into the
plugin. EXL3 itself is **MIT**, so it's the only legally usable base — which,
happily, is also the technically better one (see below).

## 1. What EXL3 actually is

EXL3 is a tail-biting trellis-coded quantizer (TCQ), the same family as
Cornell's QTIP, but an independent reimplementation rather than a port —
`doc/exl3.md` calls it "a variant of QTIP" that "deviates from QTIP in how
tensors are regularized and packed." Concretely:

- **No stored codebook.** A weight's value is generated by a ~3-instruction
  hash of the trellis bit-window (multiply + bit-hack + add), not a table
  lookup. Three procedural codebooks exist (`3inst`/QTIP-original, `mcg`,
  `mul1`); `mul1` is current default. Zero memory cost, decode is fused
  directly into the tensor-core MMA pipeline — weights are never
  materialized as a dense matrix at small/medium batch size.
- **Per weight matrix, only three tensors are stored:** `trellis` (packed
  int16 bitstream), `suh`/`svh` (fp16 per-input/output-channel scale+sign
  vectors), plus optional `bias`. No group size, no zero point, no g_idx.
- **Regularization** folds RMS scales into `suh`/`svh` and applies a
  **blockwise Hadamard transform in blocks of 128** on both the input and
  output dimension, plus LDLQ (GPTQ-style sequential error-feedback)
  quantization tile-column by tile-column. This is where EXL3 diverges from
  vanilla QTIP and is *not* optional — it's baked into every checkpoint.
- **Bit width is 1–8, integer per layer**; fractional average bpw (e.g. 3.75)
  is achieved by mixing integer-K layers across the model, not a
  continuously-variable per-weight code.
- **File format is exactly what you'd hope**: standard safetensors +
  `config.json` with a `quantization_config` block, plus (for models quantized
  since ~v0.0.2) a `quantization_config.json` giving an authoritative
  per-layer map of bits/codebook — the single most useful file for a loader.
  Tensor keys match the original HF model 1:1, which is explicitly why the
  README calls out vLLM as a plausible future backend.
- **License: MIT**, no copyleft, no vendored-code encumbrance found in the repo.

## 2. Kernels

All raw CUDA + inline PTX (`mma.sync.aligned.m16n8k16`, `cp.async`), no
Triton, no CUTLASS, Marlin-inspired. Effective floor is **sm_80 (Ampere)**;
official wheels build for 8.0/8.6/8.9/9.0/10.0/12.0. **No ROCm support**
(explicitly listed as a to-do in the README).

Four dispatch paths depending on batch size and codebook, chosen at runtime:

| path | when |
|---|---|
| cooperative fused GEMM (decode fused into MMA, 4 autotuned tile shapes) | general case |
| fp16 GEMV | m ≤ 8, K ∈ {2,3,4} |
| int8-activation GEMV (`dp4a`) | `mul1` codebook only, small batch |
| **reconstruct-to-fp16 + cuBLAS hgemm** | m > 144 (`AUTO_RECONSTRUCT_THRESHOLD`) |

That last row matters most for vLLM: exllamav3 *itself* falls back to
dequantize-then-dense-matmul for large batches/prefill. A plugin could ship a
correct-but-slow v1 using only the `reconstruct()` op + `torch.matmul`, then
layer in the fused low-batch kernels — a good incremental path.

Two integration hazards worth flagging early:
- Kernels launch via `cudaLaunchCooperativeKernel` with a device-global lock
  buffer, and use **runtime autotuning with an on-disk cache** keyed by
  `(shape, device, cc, ...)`. Both need verification against vLLM's CUDA-graph
  capture and multi-process TP workers (first-use cache writes from N worker
  processes racing is a real question, not yet answered here).
- MoE has genuine first-class support (`exl3_moe`, `exl3_mgemm` pointer-table
  batched kernels with fused top-k weighted reduction) — good news, but it's
  shaped around exllamav3's own MoE module, not vLLM's `FusedMoE` interface,
  so it needs an adapter, not just a passthrough.

## 3. QTIP / QuIP / YAQA lineage — why EXL3, not the academic repos

- **QUIP** (2023): scalar quant + incoherence processing + LDLQ rounding. No
  license file at all (all-rights-reserved by default).
- **QuIP#** (2024): adds Hadamard incoherence + E8 lattice vector
  quantization (8-dim codebook, hard ceiling on VQ dimension). GPL-3.0.
- **QTIP** (2024): replaces the codebook with trellis-coded quantization —
  effective quantization dimension 256 instead of ≤8, via a *bitshift
  trellis* (sliding 16-bit window decode, fully parallel/random-access) and
  procedural codes. This is the idea EXL3 borrows. GPL-3.0. Its own reference
  kernels, however, are a poor integration target even ignoring the license:
  matvec-only, no batched GEMM, and dispatch is **64+ hand-written
  per-shape template instantiations** compile-time-bound to specific Llama
  hidden sizes — a new model shape requires editing and recompiling the
  kernel source. EXL3's kernels solve this with runtime shape dispatch and a
  real fused GEMM, and are MIT. Even turboderp notes in `doc/exl3.md` that he
  "was not able to make regular QTIP inference work" — corroborating that the
  reference kernels are fragile.
- **YAQA** (2026, ICML): a *rounding algorithm* replacement for LDLQ that
  minimizes end-to-end KL divergence via a Kronecker-factored Hessian sketch,
  not a new storage format. Its own paper is explicit: "YAQA does not affect
  the inference efficiency of the quantized model... adding no inference
  overhead" — it's quantizer-agnostic and produces ordinary QTIP-format
  checkpoints. Verified at the source level: YAQA's repo is a fork of QTIP's
  with the CUDA inference kernel **byte-identical**; the only kernel diff is
  15 extra template instantiations for a model dimension QTIP didn't cover.

**Implication:** YAQA is not something to integrate into a vLLM plugin at all
— it's an *upstream quantizer* improvement. Since EXL3 is not bit-compatible
with QTIP (different regularization/packing/codebook), "load YAQA models in
an EXL3 runtime" doesn't work as-is. The available follow-on project, if
useful, is porting YAQA's rounding algorithm (reimplemented from the paper,
not copied — it's GPL) into exllamav3's own quantizer to produce better *EXL3*
checkpoints, using EXL3's existing MIT kernels unchanged. That's a completely
separate, orthogonal effort from the vLLM backend work and doesn't block it.

## 4. The vLLM plugin path

Confirmed via the official plugin docs and the `vllm-gguf-plugin` repo
(carved out of vLLM core, same eviction rationale as above):

- **Discovery**: a Python entry point in group `vllm.general_plugins` pointing
  at a `register()` function, loaded once per process (frontend, engine core,
  each worker) — `register()` must be idempotent.
- **Registration API is stable and public**: `register_quantization_config`
  (decorator) + `QuantizationConfig` ABC
  (`vllm/model_executor/layers/quantization/base_config.py`) — implement
  `get_name`, `get_supported_act_dtypes`, `get_min_capability`,
  `get_config_filenames`, `from_config`, `get_quant_method`. Pair it with a
  `QuantizeMethodBase` (`create_weights`, `apply`, `process_weights_after_loading`).
- **Custom ops**: register into your own `torch.ops` namespace (not vLLM's),
  either via a C++ extension using PyTorch's stable ABI, or
  `vllm.utils.torch_utils.direct_register_custom_op` for a Python-level
  wrapper — either way you need `torch.library.register_fake` impls for every
  op so `torch.compile`/CUDA-graph capture doesn't break.
- **Everything below the registration API moves fast** — vLLM makes no
  compatibility promise beneath it. The GGUF plugin doesn't pin a vLLM
  version; it runs nightly CI against vLLM `main` and patches breakage. Budget
  for that maintenance model, not a "write once" one.
- **EXL3 skips GGUF's hardest parts.** GGUF needed three monkeypatches
  (`EngineArgs`, speculator probe, diffusers loader) because it's a *container
  format* — vLLM has to be taught `model=repo:Q8_0` isn't a normal HF repo.
  EXL3 checkpoints are ordinary HF repos with `quantization_config` in
  `config.json`, so the standard `from_config`/`override_quantization_method`
  path is sufficient. No custom model loader, no config-parser registration.
- **Use `weight_loader_v2` from day one.** This is precisely the thing GGUF
  and bitsandbytes *didn't* do, and is the stated reason they're being
  evicted (they inject branches into shared `linear.py`/`fused_moe/layer.py`
  code instead). `vllm.model_executor.layers.linear` exposes
  `register_weight_loader_v2_supported_method` for this.
- **Recommended architecture** (mirrors `vllm-gguf-plugin`'s layout, minus
  the container-format pieces):
  ```
  vllm_exl3_plugin/
    plugin.py                 # register(): register_quantization_config("exl3")(EXL3Config)
    quantization/
      config.py                # EXL3Config(QuantizationConfig)
      linear.py                 # EXL3LinearMethod, weight_loader_v2-native
      fused_moe.py               # adapter over exl3_moe/exl3_mgemm -> FusedMoE
    ops.py                       # dispatch wrapper around exllamav3_ext calls,
                                  # torch.compile-safe custom op, register_fake
  ```
  Depend on `exllamav3` as a pip dependency and **call into its existing
  compiled extension** rather than rebuilding kernels — this is the single
  biggest scope reduction versus the GGUF plugin, which had to build and ship
  ~6000 lines of its own CUDA.

## 5. What the old QUIP branch is (and isn't) good for

`chu-tianxiang/vllm-gptq@quip_gemv` is a dead fork against vLLM 0.2.6
(Dec 2023 – Jan 2024). Its registration API (`_QUANTIZATION_CONFIG_REGISTRY`
dict, `LinearMethodBase.create_weights` returning a dict) predates
`register_quantization_config` entirely and shares zero surface with current
vLLM — there's nothing to port. It's useful only as confirmation of what
*not* to inherit, since its documented limitations are precisely the gaps an
EXL3 plugin needs to close rather than repeat:
- Hard-errors on tensor parallel ("Currently Quip doesn't support tensor
  parallel yet").
- No fused/merged QKV or gate-up weights — one quantized matmul per
  projection.
- Falls back to full dequant-to-fp16 above batch 32 (EXL3's own threshold,
  144, is better but the same shape of problem).
- Mutates layer state on first forward call and allocates dense scratch
  inside `create_weights` — incompatible with CUDA graphs.

## 6. Hard problems (where a spike should focus)

1. **Tensor parallelism vs. the blocked Hadamard transform.** EXL3's Hadamard
   transform operates in fixed blocks of 128 across the *entire* input or
   output dimension of a tensor. A vLLM TP shard is a contiguous slice of that
   dimension. Whether this "just works" depends on whether TP shard
   boundaries land on 128-element boundaries for the TP degrees vLLM actually
   uses (2/4/8) across the model dimensions that get sharded (usually true for
   standard hidden sizes, but needs to be verified per-architecture, and
   breaks for odd TP degrees or small models). This is the single largest
   open technical question and should be the first thing prototyped —
   everything else in this report is comparatively well-understood.
2. **Fused QKV / gate-up projections.** vLLM merges these into one Linear for
   throughput; EXL3 quantizes each projection separately with independent
   `suh`/`svh`. Need a "stacked" linear method that runs one launch over
   several separately-quantized weight tensors — the existing
   `exl3_mgemm` pointer-table kernel (already used for MoE expert fan-out)
   looks like the natural mechanism to reuse here, but that's untested.
3. **Batch-dependent kernel dispatch + CUDA graphs.** Four kernel paths
   selected by batch size (including a full dequant fallback above 144 rows)
   need to be wrapped behind one opaque custom op, GGUF-plugin-style, so
   `torch.compile`/graph capture sees a stable op rather than Python branching.
4. **Cooperative-launch + autotune-cache behavior under vLLM's multi-process
   TP workers** — needs direct testing, not just code reading.
5. **Format immaturity.** No formal spec exists yet (`doc/exl3.md` says one is
   "coming"); the on-disk format has already changed once (`su`/`sv` →
   `suh`/`svh`) and the default codebook has changed. A plugin will need to
   track exllamav3 releases fairly closely and test against specific
   checkpoint versions, not just "the format."
6. **Ecosystem size**: ~1700 HF repos matching "exl3" by name (rough count,
   likely a few hundred distinct base models, heavily community-uploaded, not
   vendor-driven) — real but meaningfully smaller than the GGUF/AWQ
   ecosystems. Worth weighing against integration effort.

## 7. Suggested phased plan

- **Phase 0 (spike, days not weeks):** single-GPU, TP=1, no CUDA graphs.
  `register_quantization_config`, an `EXL3LinearMethod` that calls
  `exllamav3_ext.reconstruct()` + `torch.matmul` (skip the fused kernels
  entirely at first). Goal: prove the registration path and confirm a
  quantized checkpoint loads and generates correct tokens through vLLM's
  forward pass.
- **Phase 1:** swap in the real fused GEMM/GEMV kernels behind a
  `direct_register_custom_op`; validate under vLLM's actual serving loop
  (continuous batching, CUDA graph capture, prefix caching).
- **Phase 2:** tensor parallelism — resolve the Hadamard-block-128 sharding
  question first; add the stacked/fused-QKV linear method.
- **Phase 3:** MoE via `exl3_moe`/`exl3_mgemm` adapted to `FusedMoE`.
- **Phase 4:** packaging (stable-ABI wheel or depend on exllamav3's own
  extension directly), CI against vLLM main, publish as an installable
  plugin — same shape as `vllm-gguf-plugin`.
- **Not on this critical path:** a YAQA-quality-improved EXL3 quantizer. That
  is a separate, later, quantizer-side project (port YAQA's rounding
  algorithm into exllamav3's LDLQ step) that produces better checkpoints for
  the same runtime — worth doing eventually, irrelevant to whether the vLLM
  backend ships.
